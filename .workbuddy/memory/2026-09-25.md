## 调研：用 aot-compiler 实现 tinyjsapp 的可行性
- 结论：**可行但属"重写而非编译"**。tinyjsapp 是 JS（txiki.js）写的，aot-compiler 只编译 PHP；其全部原生能力（窗口/菜单/托盘/对话框/音频/钥匙串/TouchID/OCR/录屏/通知）都在 C++ `native/launcher-*.cc` 里，与语言无关，MIT 许可可直接复用。
- 推荐架构：保留 tinyjsapp 的 C++ launcher（cmake 单独构建）作为原生层；用 aot-compiler 把"后端宿主 + CLI（`new/dev/build/publish`）"重写为 PHP 并编译为 `bin`；复刻 launcher↔后端的换行协议 `CALL <id> <json>` / `RET` / `GOT` / `DLG`（unix socket / named pipe）。
- 关键约束：必须用 `bin` 模式（链接 libphp，有 socket/proc_open）；`--nano` 模式无 socket/网络，无法承载桥接 → 失去 tinyjsapp ~6MB 单文件优势。aot-compiler 为 GPL-3.0，分发需评估。
- 报告产物：`D:/git/php/typephp-gui/tinyjsapp-aot-compiler-feasibility.md`（含改动清单 A1–A11、Phase 0–5 实施计划）。
- 取证：tinyjsapp 源码经 xget 代理获取（cli.js / runtime/tiny.js / launcher-win.cc / LICENSE=MIT）；aot-compiler 文档 README-CN、INCOMPATIBLE_PHP_FEATURES、MIXED_CPP_PHP、EMBEDDED_FILES。

## 补充：nano 缺 socket/进程 → 仍可保持小巧的桥接方案
- 关键洞察：**单独加 C++ 网络库救不了体积小**——nano 裁的是 PHP 层 ext-sockets/proc_open；要桥接 C++ 库给 PHP 必须走混合 C++/PHP，而那是 `bin` 模式（链接 libphp），体积已大。"小库+nano"是伪组合。
- 真小巧路线：**让 C++ launcher 当父进程/入口**，spawn aot-compiler 编出的 PHP `nano` 子进程，二者经子进程 stdin/stdout 走 tinyjsapp 的 `CALL/RET` 帧。PHP 侧零 socket/进程 → 可留 nano，体积接近原生 launcher（~6MB），且复用 MIT 的现有 C++ 原生层。
- 待验证：nano file-only stream 是否暴露 `php://stdin`/`php://stdout`（建议 hello-nano 实测 `file_get_contents('php://stdin')`）。
- 若坚持 PHP 侧补能力：libuv(~1MB, txiki.js 同款, socket+spawn 一体) / nng(~300KB, IPC 帧语义最佳) / µSockets(~150KB) / 裸 POSIX+Win32(0KB, launcher 已在用)。
- 产物：`tinyjsapp-nano-ipc-addendum.md`（与可行性主报告并列）。

## session 14（Phase 16b-1 续：stdio 三通道分离 + 把 kit 当交付物来验）

- 🐛 **bug #14：子进程 stderr 被并进帧通道**。`spawn_proc` 原本 `si.hStdError = child_out` → 后端任何诊断都变成**帧流里的畸形帧**；一直没暴露是因为 **launcher 对不认识的帧直接丢弃**（协议设计），所以只是"脏"。真风险是 **PHP 错误路由随版本变化**：实测 **8.5 的 notice 走 stderr、Cygwin 的 7.4 走 stdout** → 同一后端在不同 PHP 上行为不同，**炸在哪取决于 notice 落在哪两个帧之间**。修法：**stdin/stdout 走帧 + stderr 独立第三条管道**，shim 只排空、只写日志（`[shell] backend stderr: …`）、**永不转发**。
  - **排空是机械必需**：匿名管道 ~64KB 写满后**写者永久阻塞** → 话多的后端会在协议中途卡死，症状伪装成"后端不应答"。**"子进程 stderr 不管"的设计必须先回答"谁在读它"。**
  - 实现：`spawn_proc()` 加第三通道 `child_err`（Windows 注释写死 `NEVER child_out`；POSIX `dup2(child_err,2)`，未给才回退到 `child_out`）；新增 `drain_stderr()` **按行重组**（半行等 `\n`，残行 8KB 上限）；**`kill_proc(php)` 之后再排空一次**（缓冲里还有临死输出）；`done:` 处 `io_close(hReadStderr)`。
- **验证方式本身是重点：诱饵 + 正向对照**（新增 `posix-test/stderr-channel.sh` + `mock_backend_noisy.py`）。对抗后端在**被回答的同一个 id** 上往 stderr 写**与真实应答无法区分**的诱饵 `RET <id> 0 …` + 一条**无换行的半行**。因为客户端等的是**前缀匹配**，合并后它会**把诱饵当成该 id 的答复**，真实 RET 晚一拍到达、报错指向**下一个**调用（会把人带偏）。
