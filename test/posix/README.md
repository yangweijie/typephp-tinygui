# POSIX verification kit for the TypePHP↔tinyjsapp shim

`shim/backend_shell.cpp` is one cross-platform source. Its **Windows** half has
been compiled and run end-to-end many times (`tinyjs dev --typephp`, the packaged
`dist/` app). Its **POSIX** half was written but *never compiled* — the Windows
dev box appeared to have no way to build it:

| Attempted route | Why it fails |
|---|---|
| MinGW g++ 13.2.0 | no `fork` / `execv`, no `sys/un.h` |
| MSYS2 (`/d/msys64`) | only mingw/ucrt/clang toolchains installed — no msys g++, no `sys/un.h` |
| Docker Desktop | installed, but no `docker` CLI on PATH |
| WSL | only a stopped `docker-desktop` utility distro |
| **Cygwin g++** | **works — see below.** Cygwin is a real POSIX target: it does *not* define `_WIN32`, and its runtime has `fork`/`execv`, `poll`, `sys/un.h` and `AF_UNIX`. |

So the POSIX half **has been compiled and run locally** (Cygwin 3.5.3, g++ 11.4.0):
every runnable tier passes. This kit still exists to make the verification **one
command** on any POSIX host and to isolate the actual risk: the AF_UNIX endpoint +
the poll/read pump. It deliberately needs **no GTK/webkit and no display**, so you
do not have to build `launcher-linux` (which requires `libgtk-3-dev` +
`libwebkit2gtk-4.1-dev`) just to find out whether the transport works.

## Run it

One command runs everything, or pick a single question:

```bash
cd test/posix
./all.sh                              # host probe + every tier -> one evidence log
```

```bash
./run.sh                              # dev mode: endpoint + pump + teardown (5 calls)
N_CALLS=50 ./run.sh                   # more frames
./launch-mode.sh                      # PACKAGED entry (argc==1, <name>.conf) — the shipping path
./tier2.sh                            # real PHP backend instead of the mock (auto-detects PHP)
./stderr-channel.sh                   # stdout/stderr isolation, with a positive control
```

It needs `g++` (and a C compiler for the client) and `python3` only for the fixture
self-test. Exit `0` = all checks passed.

Local run on Cygwin: **50 PASS / 0 FAIL** across the host probe, tier 1, tier 2,
launch mode and the stderr probe. See `cygwin-all.log` (combined transcript — it is
regenerated by `all.sh`), plus `tier2-shim.log` and `launch-mode-shim.log` for raw
frame-by-frame shim logs.

### On Cygwin (no Linux box required)

```bash
/d/cygwin64/bin/bash -lc 'cd /cygdrive/d/git/php/typephp-gui/test/posix && bash all.sh'
```

That is a complete, honest run — **with two caveats you must state when quoting it:**

- Cygwin is a POSIX *emulation* layer over the Windows kernel, so this proves the
  **code path** (compile + endpoint + pump + spawn + teardown), not glibc/Linux
  syscall behaviour. It also cannot produce a shippable Linux binary.
- It does **not** replace tier 3 or tier 4: `--nano` freestanding size needs a
  Linux `tpc` build, and `launcher-linux` needs GTK. Those still need Linux.

### On a remote Linux box

Any ssh-reachable box works:

```bash
scp -r test/posix <host>:/tmp/ && ssh <host> 'bash /tmp/posix-test/run.sh'
```

If you use the Radeon Cloud box, `rc exec` sources `/workspace/env.sh` and defaults
to `/workspace`, so:

```bash
"$PY" "$RC" push test/posix /workspace/posix-test
"$PY" "$RC" exec -- bash /workspace/posix-test/run.sh
```

If `rc doctor` reports the `radeon-cloud` ssh alias is missing, that box is simply
unreachable — configure the alias first (see the `radeon-cloud` skill). That is a
prerequisite, not something to guess at. You do not *need* it any more for tiers
1–2 or launch mode: Cygwin covers those.

## What it actually checks

**`run.sh` (dev mode — the launcher is the parent)**

1. **Compiles** with `-Wall -Wextra` — the branch Windows could not check at all.
2. **Endpoint**: `socket(AF_UNIX) + bind + listen` produces a listening socket at
   the path handed in on `argv[1]`; the shim logs `transport=unix-socket`.
3. **Pump, no coupling**: the mock launcher interleaves notification frames
   (`WINSTATE`, `SYS`) — which the backend never answers — with `CALL` frames.
   A request/response-coupled proxy **hangs here**; this is the same deadlock the
   Windows side hit before switching to a polling pump.
4. **Frame ordering**: the backend's `EVAL@*` window frame arrives *before* the
   `RET` for the same call, and the startup `READY` banner survives the pump.
5. **Teardown**: when the client closes, the shim notices, exits `0`, logs
   `launcher closed`, and **unlinks the socket file** (a leftover socket would
   block the next `bind()`).

**`launch-mode.sh` (packaged mode — the shim is the entry, `argc==1`)**

This is the path a Linux user would actually run, and it is a *different* code
path from dev mode: the entry reads `<exe_dir>/<exe_stem>.conf`, creates the
endpoint itself, spawns the backend, then spawns the **stock** launcher as its
client with `launcher <html> <endpoint> [title] [WxH] [version]`. It checks conf
parsing, `app=`/`launcher=` resolution against the exe directory, the exact argv
**order** handed to the launcher, the no-stdio spawn (POSIX peer of
`bInheritHandles=FALSE`), and that teardown does not orphan the launcher.

Two notes on how it is written:

- The launcher's stdout is `/dev/null` in this mode, so the mock launcher reports
  the argv it received **as a frame** — the shim logs every forwarded frame, which
  makes that log the assertion source.
- The orphan check has a **positive control** (a live process under a matching
  name is first proven visible). The first version of that check "passed" simply
  because nothing was running — a negative assertion with no positive control is
  worthless. Cygwin's `ps -ef` prints the *resolved absolute path* and ignores
  `argv[0]`, so the matcher keys on binary names.

**`stderr-channel.sh` (stdout and stderr must not be the same pipe)**

The shim gives the backend **three** stdio channels: stdin/stdout carry frames,
stderr is drained into the shim's own log and never forwarded. This script proves
that separation is real rather than merely intended, using a backend that is
actively hostile on stderr:

| Run | Decoy written to | Expected |
|---|---|---|
| A | stderr | protocol stays clean; the decoy appears in the shim log as `[shell] backend stderr: …` |
| C | stderr, but the **real `backend.php`** | `tiny.log(msg)` lands in the shim log, never on the wire |
| B | **stdout** (positive control) | the client **must fail** |

Run B is what gives run A its teeth: "the client passed" is worthless on its own,
since it could just mean the decoy was never written. Flipping one env var and
watching the same client break — and the decoy count in the shim log flip from
`0 forwarded` to `1 forwarded` — is what shows the decoy is genuinely
protocol-breaking. The decoy is a `RET <id> 0 …` for the id being answered, i.e.
**ambiguous with the real reply**, rather than mere prose.

Why this earned a tier: PHP's own error routing is version-dependent — PHP 8.5
sends notices to stderr, Cygwin's PHP 7.4 sends them to **stdout** (both verified
here) — so "which channel do diagnostics arrive on" is not something the shim can
assume. Keeping them separate is the only arrangement that survives both. Draining
stderr also matters mechanically: a pipe nobody reads fills at ~64 KB and the
writer then blocks forever, so a chatty backend would wedge itself mid-protocol.

## Tiers — how far to take it

| Tier | Backend | Extra setup | What it proves | Local (Cygwin) status |
|---|---|---|---|---|
| **1 (default)** | `mock_backend.py` | none | transport + pump + teardown | ✅ **11/11 pass**, 25-call stress |
| **2** | real PHP (`tier2.sh`) | a PHP ≥ 8.0 binary | the real `backend.php` logic over the POSIX shim | ✅ **11/11 pass**, 12 CALL → 12 RET → 24 EVAL |
| **3** | AOT binary (`tpc`) | aot-compiler for **Linux** | nano size/behaviour — the original question | ❌ needs Linux (Cygwin cannot host a Linux ELF) |
| **4** | + `launcher-linux` | `libgtk-3-dev`, `libwebkit2gtk-4.1-dev`, `xvfb-run` | the true window end-to-end | ❌ needs Linux |

Orthogonal to the tiers: `launch-mode.sh` covers the **packaged-entry** path
(`argc==1` + `<name>.conf`) rather than a different backend — ✅ **13/13 pass** —
and `stderr-channel.sh` covers the three-stdio-channel contract — ✅ **15/15 pass**.

### Tier 2 — real PHP backend

```bash
./tier2.sh                                             # auto-detects a PHP >= 8.0
PHP_EXE=/d/cygwin64/bin/php.exe ./tier2.sh             # explicit (7.4 is refused)
N_CALLS=20 ./tier2.sh
BACKEND_PHP=/path/to/your/backend.php ./tier2.sh       # when it is not the default
```

The default is **not a guarantee** — these scripts ship standalone, and the backend
under test is usually *yours*. When it is missing, tier 2 and the real-PHP step of
`stderr-channel.sh` **skip** with exit `2` and name the override, rather than failing
on a path you never chose.

#### How the scripts find the shim (`resolve-root.sh`)

This kit has two supported homes, so no script hard-codes a relative path:

| Home | `backend_shell.cpp` lives at | `backend.php` lives at |
|---|---|---|
| **in-tree** — `<repo>/test/posix/` | `<repo>/shim/backend_shell.cpp` | `<repo>/src/backend.php` |
| **standalone** — copied out of the repo | `../backend_shell.cpp` (beside the kit) | `../backend.php` |

Every script sources `resolve-root.sh` and calls `typephp_locate "$HERE"`, which
walks up looking for `composer.json` (the one file guaranteed to sit at the repo
root). If it finds one you get the in-tree paths; if not, the standalone ones. It
sets three variables: `TP_ROOT` (empty when standalone), `TP_SHIM_SRC`, and
`TP_BACKEND_DEF`. Reorganising the repo therefore does **not** break the kit.

#### …and everything else that depends on which home it is (`resolve-root.sh`, cont.)

Finding the sources was only half of it. Two more answers differ per home, and
both were wrong in ways that **only show up in the standalone copy** — which is
the copy that gets published, so they were the interesting ones:

| | in-tree | standalone | why |
|---|---|---|---|
| scratch | `<kit>/.work` | `$TMPDIR/typephp-kit.XXXXXX` | the kit ships *inside* a skill directory, and the synced copy is diffed against the repo to prove the two match. A run that writes into the kit directory turns that diff into noise, which is how a stale copy hid on the first attempt. Every script prints the path it used. |
| socket | `$WORK/app.sock` | same — unless `WORK` is long, then `$TMPDIR/tpkit.XXXXXX/app.sock` | `sun_path` is ~108 bytes (104 on macOS). `$WORK/app.sock` was 108 chars *exactly* under the skill directory: `bind()` failed and `run.sh` reported the unhelpful `socket never appeared`, while the identical kit passed in-tree purely because `/d/git/php/typephp-gui` is shorter. |

`typephp_default_work` and `typephp_socket_path` both **set variables**, they do
not print — `SOCK="$(typephp_socket_path …)"` would run in a subshell and the
`TP_SOCK_TMP` it needs to hand back would be discarded with it. An explicit
`WORK=` always wins over both defaults.

Three further traps the standalone home exposed, all now fixed:

- **`$WORK` did not exist yet.** `all.sh` compiled `host_probe` into `$WORK/`
  before anything created it (`ld: cannot open output file … No such file or
  directory`). Each tier created it for itself, so only step `[0]` was hit.
- **A "default" that ignored `WORK=` made nine empty temp dirs.** `all.sh`
  exports `WORK` to its children so they all share one scratch dir; each child
  then called `typephp_default_work` anyway, which made a temp dir *before*
  discovering it had no use for it. Five or six abandoned directories per
  standalone run. `typephp_default_work` now returns early when `WORK` is set.
- **A hard-coded socket path made an assertion blind.** In launch mode the
  *entry* names the endpoint (`<exe_dir>/app.sock`, or the shim's own
  `/tmp/tinyjs-typephp-<pid>.sock` fallback when that would overflow `sun_path`).
  `launch-mode.sh` asserted on `$WORK/app.sock`, so its "socket file unlinked on
  exit" check passed **vacuously** in exactly the case where the fallback fired —
  i.e. in the shipped home. It now reads the chosen path back out of the shim log
  (`transport=unix-socket pipe=…`) and asserts on that, and says which of the two
  forms was used. Both branches are covered: the derived one in-tree, and the
  fallback by pointing `WORK=` at a deep directory:

  ```bash
  # a work dir whose app.sock exceeds sun_path, so the shim must fall back
  LONG=/tmp/$(printf 'd%.0s' $(seq 1 120))
  WORK=$LONG/lw ./launch-mode.sh
  #   [PASS] endpoint is the shim's /tmp fallback (/tmp/tinyjs-typephp-1234.sock)
  #   [PASS] socket file unlinked on exit
  WORK=$LONG/rw ./run.sh
  #   [PASS] AF_UNIX listening socket created: /tmp/tpkit.XXXXXXXX/app.sock
  ```

  Those two runs are also what exercises `typephp_socket_path`'s own temp dir, and
  the `EXIT` trap that removes it.

`tier2.sh` generates a wrapper the shim can exec (`execv` is called with **zero
arguments**, so the backend must be directly runnable — on POSIX a shebang'd script
qualifies, on Windows it would have to be a real `.exe`):

```php
#!/path/to/php
<?php
require '/abs/path/to/backend.php';
main();          // mandatory: tpc auto-invokes main(), stock PHP does not
```

Two path rules the helper encodes, both of which cost a debugging round:

- **`TYPEPHP_APP` reaches PHP as the *script argument*.** A Windows PHP cannot open
  a `/cygdrive/...` path, so pass a Windows-style path (`cygpath -m`). The shim's own
  `execv()` accepts either form. Symptom of getting it wrong: the first frame on the
  wire is `Could not open input file: /cygdrive/…`.
- **`require` must be absolute.** `__DIR__` hands Windows PHP a Cygwin path.

Also check the PHP version: `src/backend.php` uses `str_starts_with`/`str_contains`,
so **PHP 7.x will not do** (Cygwin's bundled PHP 7.4 is a trap here). `tier2.sh`
verifies `PHP_VERSION_ID >= 80000` and refuses otherwise — and auto-detects a
suitable interpreter (Cygwin's `php` on PATH is the 7.4 one, so it walks on to the
tpc distro's 8.x).

### Tier 3 — the size measurement that started this

```bash
tpc --nano   backend.php -o app_nano
tpc           backend.php -o app_bin        # for comparison
ls -l app_nano app_bin
ldd app_nano        # the point: freestanding nano must NOT pull in libphp
BACKEND_APP=$PWD/app_nano ./run.sh
```

This is the one measurement that decides whether the "小巧路线" is real on Linux:
Windows `--nano` is only a policy wrapper around the full DLL runtime (identical
imports, ~1.5% smaller, and it SIGSEGVs on teardown), so Linux is the only place
the freestanding runtime can pay off. Remember the backend must avoid every
function in `NANO_UNSUPPORTED_FUNCTIONS` (see the `aot-compiler-windows-build`
skill) — `src/backend.php` was cleaned for this.

(An earlier revision of this file ended that sentence with a warning that `log`
writes to stderr, "which is the frame channel". That is no longer true and the
warning has been removed rather than reworded: the shim now gives stderr its own
pipe, so a `fwrite(STDERR, …)` is a diagnostic, not a protocol hazard.)

### Tier 4 — the real window

```bash
sudo apt-get install -y libgtk-3-dev libwebkit2gtk-4.1-dev xvfb
g++ -std=c++17 -O2 -o launcher-linux ../tinyjsapp/native/launcher-linux.cc \
    $(pkg-config --cflags --libs gtk+-3.0 webkit2gtk-4.1)
```

## Cygwin gotchas (each one cost a debugging round)

1. **The shim needs a feature-test macro.** `-std=c++17` defines `__STRICT_ANSI__`,
   after which libc hides POSIX declarations. On glibc the g++ driver injects
   `_GNU_SOURCE` for you, so this hides until you build somewhere else: on
   Cygwin/newlib, `readlink()`, `kill()` and `setenv()` all came back as *not
   declared in this scope*. Fixed in the source itself (a `#define _GNU_SOURCE`
   guarded by `#if !defined(_WIN32)`, placed **before every `#include`** — a
   visibility macro has no effect after the first header). Same fix in
   `mock_launcher.c`.
2. **A Python client cannot talk to a C server on Cygwin.** CPython's `AF_UNIX`
   and native Cygwin `AF_UNIX` appear to be different planes:

   | server | client | result |
   |---|---|---|
   | C | C | `accept()` OK |
   | C | Cygwin Python | `accept()` **ECONNABORTED (113)** while the client's `connect()` *succeeds* |
   | Cygwin Python | C | python `accept()` "OK" but reads **unrelated garbage**; the C client gets `ECONNREFUSED` |
   | Cygwin Python | Cygwin Python | works |

   So the kit would have reported a shim failure that was really a client-runtime
   artefact. Hence `mock_launcher.c`: the real launcher is C++ anyway, so the C
   client is the more faithful stand-in. `mock_launcher.py` is kept as the
   cross-platform protocol oracle used by `selftest_fixtures.py`.
3. **Cygwin's PHP is 7.4** — too old for `backend.php`. Point tier 2 at a PHP 8
   (`PHP_EXE=…`); the tpc distro's `php.exe` (8.5) works, driven through a Cygwin
   shebang.
4. **A wrapper script on `PATH` is not enough** — `execv()` does not search `PATH`,
   and the shim always calls it with the bare path you set in `TYPEPHP_APP`.

## Files

- `all.sh` — runs `host_probe` + every tier and writes one combined evidence log.
  This is the reproducible one-command entry point; prefer it to hand-assembling
  env vars, which is how the log and the scripts drift apart.
- `run.sh` — the orchestrator; runs the fixture self-test, builds the shim and the
  C client, and asserts the sequence above. **Refuses to run on Windows** (there the
  shim takes the `_WIN32` path and serves a named pipe, so every AF_UNIX assertion
  would fail for the wrong reason) — it exits `2` explaining why. **Cygwin is
  accepted deliberately** (see below). `CLIENT=py|bin|auto` overrides the client.
- `launch-mode.sh` — verifies the **packaged entry** (`argc==1`, `<exe_stem>.conf`):
  stages a portable app folder, runs the entry with no arguments, and asserts conf
  parsing, launcher argv order, the pump, and orphan-free teardown. See above.
- `stderr-channel.sh` — verifies that stdout and stderr are **not** the same pipe,
  with a positive control that must fail. See above.
- `host_probe.c` — optional but useful before blaming the shim on a new host: proves
  `AF_UNIX bind/listen`, `fork+execv+dup2`, `accept()` returning a **new fd**,
  `poll(0)`-then-`read` framing, socket EOF, `SIGPIPE` ignore and `waitpid`, printing
  `PROBE: ALL PRIMITIVES PRESENT` or exactly which one is missing.

  ```bash
  g++ -Wall -Wextra -O1 -o host_probe host_probe.c && ./host_probe
  ```
- `mock_launcher.c` — **the client the kit uses.** AF_UNIX client speaking the
  `CALL`/`RET` protocol with notifications interleaved; payload-agnostic, so it
  works against the mock backend and the real PHP one alike. Preferred over the
  Python client everywhere: no `socket.AF_UNIX` dependency, and it mirrors what
  `launcher-linux.cc` actually does. `MOCK_LOG_CALL=1` adds one `tiny.log(msg)`
  round-trip — the only backend method that writes to stderr, so it is the hook the
  stderr probe pulls.
- `mock_launcher.py` — the same protocol in Python, kept as the oracle for
  `selftest_fixtures.py` (and as a fallback when no C compiler exists). **Must stay
  in sync with `mock_launcher.c`** for the base protocol; if you change one, change
  both. (`MOCK_LOG_CALL` is deliberately *not* mirrored — it is off by default and
  only the C client can drive the Cygwin shim.)
- `mock_backend.py` — shebang'd stand-in for the AOT backend; no reply to
  notifications, window frame before `RET`, `READY` banner on startup. Writes raw
  **bytes** so its frames are identical on every platform (text-mode stdout would
  emit `\r\n` on Windows).
- `mock_backend_noisy.py` — the *adversarial* twin, used by `stderr-channel.sh`: it
  interleaves stderr noise with the reply for the same call, including a decoy
  `RET <id> 0 …` that is ambiguous with the real answer and a partially-written
  line. `NOISY_CHANNEL=stdout` turns it into the positive control.
- `tier2.sh` — generates the PHP wrapper and runs the kit against real PHP. See
  tier 2 above. Honours `PHP_EXE=` and `BACKEND_PHP=`.
- `selftest_fixtures.py` — validates the kit's own oracle. Monkeypatches
  `socket.socket` with a stdio pipe into `mock_backend.py` and then runs the real
  `mock_launcher.py` through it, so the launcher's parsing is exercised against
  the backend's actual replies **without needing AF_UNIX**. Runs anywhere,
  including Windows, and is step `[1/5]` of `run.sh` — a red oracle must never be
  mistaken for a broken shim:

  ```bash
  python3 selftest_fixtures.py     # → FIXTURES OK
  ```
- Evidence from the local Cygwin run: `<repo>/evidence/kit/cygwin-all.log` (host
  probe + tier 1 + tier 2 + launch mode + stderr probe, **50 PASS / 0 FAIL**),
  `tier2-shim.log` (raw shim log — shows the real backend turning
  `WINSTATE`/`SYS theme` into `EVAL@*` pushes and answering `ping` with `"pong"`),
  `launch-mode-shim.log` (packaged-entry frames). The in-tree run writes there
  rather than next to the kit, so the kit directory stays exactly what is synced
  into the skill; a standalone run writes to its temp work dir and prints the path.
- `.work/` — scratch: `backend_shell`, `mock_launcher`, `shim.log`, `launcher.out`,
  `build.log`, `cc.log`, `fixtures.out`, `tier2_backend.php`, `launch/` (staged
  portable folder), `stderr/` (`stderr-channel.sh`'s own shim logs for runs a/b/c,
  kept out of the way because they are per-run). Safe to delete; every script
  rebuilds what it needs. Standalone, the same layout appears under
  `$TMPDIR/typephp-kit.XXXXXX/` instead — see `typephp_default_work` above.
